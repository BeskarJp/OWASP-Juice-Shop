## [Improper Input Validation] - [Deluxe Fraud]

## General Information

* **Difficulty Level :** ⭐⭐⭐ / 6
* **Date of Resolution :** 25-03-2026

---

## Vulnerability Analysis

* **Vulnerability Name :** Insecure Business Logic
* **Affected Components :** Payment Processing API (`/rest/deluxe-membership`)
* **Severity :** <span style="color:red"> High </span>

---

## Proof of Concept (PoC)

#### 1. Enumeration & Techniques

* **Techniques used :** Web Traffic Analysis
* **Tools used :** Web Browser, Burp Suite

#### 2. Reproduction Steps

**Step 1 : Accessing the Deluxe Portal**

Navigate to the Deluxe Membership page. Initially, the application displays a message stating you are not eligible. Proceed anyway to the payment selection screen for the Deluxe upgrade.

**Step 2 : Traffic Interception**

Prepare Burp Suite and fill in any dummy data for the payment form and click the `Pay` button. Intercept the POST request.

**Step 3 : Analyzing the Payload**

The request contains a JSON body similar to this :

```JSON
{
  "paymentMode": "card",
  "paymentId": 12
}
```

The application uses these IDs to check a valid payment method was selected and processed.

**Step 4 : Privilege Escalation Confirmation**

The vulnerability lies in how the server handles unexpected paymentMode values. By tampering with the request, we can attempt to bypass the check :

```JSON
{
  "paymentMode": "none",
  "paymentId": null
}
```

**Step 5 : Verification**

The server accepts the `none` payment mode as a valid bypass, likely due to a switch-case or conditional logic that fails to default to `Reject` when an unknown mode is provided. We are immediately upgraded to Deluxe Membership without any actual funds being charged.

---

## Risk Assessment

* **Business Impact :** Direct financial loss. Users can access premium features, discounts, and exclusive content for free.

* **Technical Description of the Impact :** The server-side code trusts the client-provided paymentMode without verifying if that mode is actually "paid" or if a transaction hash was generated by a legitimate payment processor.

---

## Actions & Remediation

#### Mitigation Strategies

   - Never trust the "Success" state or "Payment Mode" sent from the client. The server must verify the transaction with the payment provider's API directly.

   - Use a strict "Allowlist" for payment modes. If the input doesn't match a valid, active payment method, the request should be rejected immediately.

#### Recommended Fixes

   - Use secure webhooks from payment gateways to update user membership status only after the payment provider confirms the capture of funds.
